# 위에 정의한 이름이 뒤에서 낱말로 다시 나오는 자리 — 전수 실측

작성 2026-08-23 · 대상 컴파일러 `e7e0c2b`(0.8.0) · 자료 `survey-names-in-prose.tsv`

## 왜 쟀는가

「NME 개발 피드백」이 P0로 든 결함 둘이 같은 규칙에서 나온다.

아래 토막에서 `→` 왼쪽은 쓴 NME이고 오른쪽은 컴파일러가 낸 파이썬이다.
프로그램이 아니라 나란히 적은 것이므로 `text`로 묶었다.

```text
수호룬은 거짓
선택을 물어봐 수호룬, 폭약
만약에 선택이 수호룬과 같으면      → if (선택 == 수호룬):   ← 어떤 입력에도 참이 안 된다
```
```text
사기는 50
직업특성은 사기와 균형 파괴        → 직업특성 = str(사기) + "와 균형 파괴"
```

둘 다 **「위에 만들어 둔 이름이면 값으로 바꾼다」**는 규칙이 낸 결과다. 규칙을
좁히려면 지금 그 규칙에 기대어 돌아가는 프로그램이 몇이고 어느 방향으로 기대는지를
먼저 알아야 한다. 그것을 쟀다.

## 무엇을 셌는가

**「낱말로 다시 나온다」의 정의** — 그 이름이 *명령의 대상*이 아니라 **자유롭게 쓴 글
안이나 비교의 한쪽**에 나타나, 컴파일러가 조사를 떼어 이름으로 알아보고 값으로 바꾼
자리. 나온 파이썬에서 `str(이름)`과 `== 이름`이 정확히 그 자리다.

`점수에 1 더해`처럼 문법이 대상을 요구하는 자리는 세지 않았다. 그 자리에서 이름을
이름으로 읽는 것은 이 규칙과 무관하게 옳다.

**대상 프로그램 160개**
- `~/nmt/needmoreeasy/examples/**/*.nme` — 72개
- `~/nmt/nme/site/src/examples.ts`의 `EXAMPLES` — 88개(영어 44 · 한국어 44)
- 컴파일에 실패한 둘(`en--error.nme`·`ko--error.nme`)은 **일부러 컴파일되지 않는
  오류 시범**이므로 제외했다. 실제로 읽은 것은 158개, 자리가 나온 파일은 71개다.

**판정**

| 판정 | 곳 | |
|---|---:|---|
| ① 값으로 바뀌어야 맞는 곳 | **1,934** | |
| ② 글자로 남아야 맞는 곳 (지금 결함) | **0** | |
| ③ 어느 쪽이어도 결과가 같은 곳 | **0** | |
| 판정 보류 | **0** | |

**② 결함이 한 곳도 없다.** 이것이 이 조사의 핵심이고, 아래가 근거다.

### 어떻게 판정했는가

기계가 확실히 가를 수 있는 것을 먼저 걸렀다.

- **참/거짓·목록·표가 글에 끼워진 자리** — `True`나 `['가','나']`가 문장에 나오므로
  사람이 읽을 글이 되지 않는다. → **0곳**
- **비교의 양쪽이 절대 같아질 수 없는 형인 자리** — 이름마다 무엇이 대입되는지
  훑어(`= True/False`·숫자·글자·`input()`·목록·표) 왼쪽이 글자 계열이고 오른쪽이
  참/거짓·숫자인 조합을 찾았다. 수호룬 사례가 정확히 이 모양이다. → **0곳**
- **담은 글자가 그 낱말과 같은 자리**(③의 정의) → **0곳**

남은 것은 「그 낱말이 그 문장에서 이름을 뜻하는가, 평범한 명사를 뜻하는가」로,
기계가 가를 수 없다. 그래서 **사람이 읽을 몫을 좁혀 전부 읽었다.**

좁힌 방법: 557개 이름 중 `~이름`·`~수`·`~값`·`~주소`·`~번호`처럼 **이름만 보아도 값을
가리키는 것이 드러나는 것**을 뺐다. 남은 것 중 한글 세 글자 이하 — 즉 평범한 낱말과
겹칠 만한 것 — 이 **47개, 자리로는 157곳**이었고, 그 157곳을 원문과 나온 파이썬을
나란히 놓고 전부 읽었다. 47개는 이렇다.

> 공색깔 · 글귀 · 금화 · 남은판 · 내것 · 논스 · 답낱말 · 답한것 · 당첨금 · 독피해 ·
> 동물 · 레벨 · 명성 · 몇번 · 모험일 · 문맥 · 물건 · 별표 · 빈바탕 · **사기** · 사람 ·
> 살것 · 쓴돈 · 운명눈 · 자리 · 저장문 · 적경험 · 적균형 · 적금화 · 적생명 · 적의도 ·
> 적체력 · 적특징 · 주머니 · 주운돈 · 준피해 · 줄 · 짐승 · 총스핀 · 최고층 · 친구 ·
> 평균 · **포만** · **피로** · 합계 · 혼돈눈 · 훔친돈

**157곳 전부 ①이었다.** 피드백 문서가 지목한 `사기`·`포만`·`피로`도 예제 안에서는
전부 옳게 읽힌다.

```text
생존 기록 · 모험일 모험일 · 포만 포만 · 피로 피로 · 사기 사기 말해줘
→ print("생존 기록 · 모험일 " + str(모험일) + " · 포만 " + str(포만) + " · 피로 " + str(피로) + " · 사기 " + str(사기))
```

## 이 조사가 밝힌 두 가지

### 1. 컴파일러는 이미 한 문장 안에서 같은 낱말을 다르게 읽는다

위 줄에서 `포만`이 두 번 나오는데 앞은 글자로 남고 뒤만 값이 됐다. 최소 재현:

```text
포만은 80
포만 포만 말해줘      → print("포만 " + str(포만))
포만이 포만 말해줘    → print("포만이 " + str(포만))
쉼 포만 쉼 말해줘     → print("쉼 " + str(포만) + " 쉼")
```

즉 「이름이면 무조건 값」이 아니라 **한 문장에 같은 낱말이 여럿이면 하나만** 값으로
바꾸는 기제가 이미 있다. 규칙을 좁힐 때 새로 만들 것이 아니라 **이미 있는 것을
넓히는** 쪽으로 볼 수 있다는 뜻이다.

`직업특성은 사기와 균형 파괴`가 어긋난 이유는 그 문장에 `사기`가 **한 번만** 나오기
때문이지, 조사가 붙어서가 아니다.

### 2. 조사로는 가를 수 없다

「조사가 붙은 이름은 값으로 바꾸지 않는다」를 실측했다. 글 안 1,713곳 중 이름이
**조사가 붙은 채로만** 나오는 것은 19곳이었고, **19곳 전부 옳게 읽힌 것**이었다.

```text
적이름의 특징은 적특징 입니다 말해줘
→ print(str(적이름) + "의 특징은 " + str(적특징) + " 입니다")
무기이름이 준피해 만큼 상처를 냅니다. 말해줘
→ print(str(무기이름) + "이 " + str(준피해) + " 만큼 상처를 냅니다.")
저장조각들은 저장문을 쉼표로 나눈 것
→ 저장조각들 = str(저장문).split(",")
```

**한국어에서 「이름+조사」로 값을 끼우는 것은 정상적인 쓰기 방식이다.** 이 축으로
좁히면 19곳이 그대로 깨지고 얻는 것이 없다.

## 따로 물으신 셈 둘

### 「대입의 오른쪽에서는 보간을 하지 않는다」로 좁히면

**①에 해당하는 자리 334곳이 깨진다** (언어 저장소 예제 314 · 사이트 예제 20).

```text
완성코드칸은 빈바탕을 0개 붙인 것      → 완성코드칸 = str(빈바탕) * 0
저장조각들은 저장문을 쉼표로 나눈 것    → 저장조각들 = str(저장문).split(",")
과일들은 줄을 쉼표로 나눈 것            → 과일들 = str(줄).split(",")
```

`나눈 것`·`붙인 것`·`이은 것` 같은 **새로 넣은 글자 다루기 문장이 전부 대입의
오른쪽**에 온다. 이 안은 살 수 없다.

### `물어봐`가 나열한 낱말이 위에 정의한 이름과 겹치는 자리

물어보는 줄 **242곳** 중, 보여 주는 글에 이미 만들어 둔 이름이 값으로 끼워진 자리는
**0곳**이었다.

수호룬 사례는 예제에 없다. 사용자가 **선택지로 보여 줄 낱말과 상태를 담을 이름을 같은
말로 지었을 때만** 생기고, 예제는 그렇게 짓지 않는다.

## 그래서 무엇이 갈리는가

- **비교 쪽(A)은 지금 고쳐도 예제가 한 곳도 깨지지 않는다.** 221곳 중 절대 참이 될 수
  없는 조합이 0곳이므로, 그런 비교를 오류로 내는 규칙을 넣어도 기존 프로그램은
  전부 그대로 컴파일된다. 문맥 추적 없이 형만 보면 된다.
- **글 쪽(B)은 예제로는 재현되지 않는다.** 1,713곳 어디에도 결함이 없다. 이 문제는
  **사용자가 평범한 명사를 이름으로 지었을 때만** 나타나고, 그때 컴파일러는 규칙대로
  옳게 하고 있으며 사람의 뜻과 어긋날 뿐이다. 규칙을 어느 쪽으로 좁혀도 지금 옳은
  1,713곳 중 상당수를 깨뜨린다.

## 덧 — 일 안에서 아래 이름이 글자로 굳는 자리 (2026-08-23 추가)

「NME 개발 피드백」이 P0로 든 세 번째 것이다. 같은 규칙의 다른 얼굴이라 같은 자리에
적는다.

```text
채울양에게 생명막대그리기라는 일:
  최대비교값은 막대최대양      → 최대비교값 = "막대최대양"   ← 글자로 굳는다
끝
막대최대양은 100
```

실행하면 `100`이 아니라 `막대최대양`이라는 낱말이 찍히고, 그 값을 계산에 쓰면
`TypeError`가 난다. 컴파일도 검사도 정리도 아무 말을 하지 않는다.

**같은 방법으로 쟀다.** 예제 160개에서 일 블록을 찾고, 그 안의 대입 중 오른쪽이
홑낱말인 것을 모아, 그 낱말이 파일 어디에서 만들어지는지로 갈랐다.

| | 곳 |
|---|---:|
| 일 블록 | 22 |
| 일 안의 홑낱말 대입 | 14 |
| — 일보다 **위**에서 만들어짐 (정상) | 3 |
| — 일 **안**에서 만들어짐 (정상) | 4 |
| — 일의 **매개변수** (정상) | 7 |
| — 일보다 **아래**에서 만들어짐 (결함) | **0** |

**결함이 0곳이다.** 그러니 이 자리를 알리도록 고쳐도 지금 예제는 하나도 깨지지 않는다.

다만 표본이 작다. **일을 쓰는 예제가 넷뿐**이고(`peace` 두 판·`rpg-tower` 두 판) 일
블록 22개가 전부 거기 있다.

### 평화는 이 함정을 겪고 나서 고쳤다

피드백 문서가 든 바로 그 줄이 지금 예제에 살아 있다 — `peace.ko.nme:118`의
`최대비교값은 막대최대양`이다. 그런데 옳게 컴파일된다. `막대최대양은 1`이 **94줄**,
일 블록이 **109줄**에서 시작하므로 이름이 일보다 위에 있기 때문이다. 문서에 적힌
회피법(「`막대최대양은 1`을 일 선언보다 먼저 두면 의도한 참조가 된다」)을 작성자가
그대로 적용한 것이다.

즉 **이 결함은 사람이 한 번 겪어야 알 수 있고, 겪고 나면 줄 순서를 바꿔 피한다.**
겪기 전에 알려 주는 것이 이 진단의 값어치 전부다.

### 고친다면 어디에 붙는가

`comparisons.rs`와 **같은 자리, 같은 모양**이다 — 파싱이 끝나고 파일 전체를 본 뒤에야
알 수 있는 판정이고, 한 줄만 보아서는 알 수 없다. 판정 조건도 좁다.

1. 일 블록 안에서 이름이 글자로 굳었고,
2. 그 이름이 같은 파일의 **일 블록보다 아래**에서 만들어진다.

매개변수와 일 안에서 만든 이름은 이미 이름으로 읽히므로 걸리지 않는다. 위에서 만든
것도 마찬가지다. 남는 것은 「아래에 있는 것을 위에서 부른」 경우 하나뿐이다.

`E0606`과 같은 물음이 따라온다 — **오류로 낼 것인가 경고로 낼 것인가.** 이쪽은
E0606보다 사정이 낫다. 글자로 굳은 것을 그대로 두어도 프로그램이 도는 경우가 있기
때문이다(그 값을 찍기만 하면 낱말이 찍힐 뿐 멈추지는 않는다). 그래서 거절보다
알림이 더 어울린다.
